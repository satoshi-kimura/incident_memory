# Phase1 仕様fix

## 1. 対象変更名

Zero to Shipped submission tag and value-first copy

## 2. 変更目的

公式ルールで要求される Startup lane のタグを `#startup` に統一する。あわせて、審査員が冒頭30秒で「実際のAWS障害を証拠から再構成し、異なる原因の過去障害と82%一致させ、前回の復旧策を再利用できる」という製品価値を理解できる文章へ変更する。

## 3. 変更対象モジュール

- docs
- web（ランディングページの説明文のみ）

## 4. 現在の仕様との関係

- 変更前: lane 名とタグが `Startups` / `#startups`。冒頭説明が抽象的で、主要デモの結果を理解するまで本文を読む必要がある。
- 変更後: 表示上の lane 名を `Startup`、タグを `#startup` に統一する。冒頭で実データ、82%一致、異なる原因、前回の復旧策と14分の回復を具体的に示す。
- 製品機能、データ、スコア、アーキテクチャは変更しない。

## 5. 既存仕様を壊す可能性

低い。文言変更のみ。既存のデモ事実と矛盾しないこと、静的プリレンダーと通常表示で同じ説明になることが回帰リスク。

## 6. 影響するシステム境界

- Web UI: ランディングページのヒーローコピー
- APIエンドポイント、ACL、認証、Terraform、インフラ、同期処理には影響しない。

## 7. fail-closed を壊す可能性

なし。認証、認可、AWSアクセス、入力処理を変更しない。

## 8. watermark・ledger・orphan cleanup・bulk failure handling への影響

すべて影響なし。文章とタグのみの変更。

## 9. 実装しない範囲

- 新機能、AWSリソース、API、データモデル、類似度ロジック
- 未確認の顧客実績、ROI、価格、導入実績の追加
- 既存マイグレーションを含むデータベース変更

## 10. 後続フェーズに回す範囲

顧客インタビュー、価格検証、定量ROIは実データが得られた後の別フェーズとする。

## 設計原則確認

- 既存アーキテクチャを維持する。
- 既存の説明責務に統合し、新しい責務や一時的回避策を増やさない。
- 将来削除予定のコードやTODOを追加しない。
- 実証済みのデモ数値だけを用い、誇張しない。

## 代替案比較

### 案A: タグとBuilder Center本文だけを修正

- メリット: 最小差分。
- デメリット: README、詳細版、公開ランディングページに古い表現が残り、審査員の入口によってメッセージが変わる。
- 不採用理由: AI審査と人間審査の双方が複数の入口を見る可能性があり、一貫性不足が残る。

### 案B: タグと冒頭メッセージを提出資料・README・公開ページで統一

- メリット: どの入口でも同じ価値が短時間で伝わる。公式タグとの不一致も解消できる。
- デメリット: 案Aより変更ファイルが増える。
- 採用理由: 内容は同じ事実の同期であり、機能変更なしで審査上の伝達リスクを直接下げられる。

## 変更影響分析

- 呼び出し元: ブラウザ利用者、Builder Center審査員、README閲覧者、AI scoring system。
- 呼び出し先: `frontend/index.html` と `scripts/prerender.py` の表示内容のみ。依存先変更なし。
- API互換性: 影響なし。
- テストへの影響: 既存の静的HTML内容確認と全バックエンドテストを回帰確認する。テスト仕様の変更は不要。
- 未確定事項: なし。
