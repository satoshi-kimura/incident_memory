# Phase2 仕様fix

## 1. 対象変更名

Progressive-disclosure UI simplification

## 2. 変更目的

初見の審査員が、ランディングページでは「何の製品か・主要デモは何か・次にどこを押すか」を、分析画面では「最も近い過去障害・何が同じか・前回どう直したか」を短時間で理解できるUIにする。既存機能と情報は削除せず、優先度の低い詳細をネイティブの展開領域へ移す。

## 3. 変更対象モジュール

- web
- docs相当のプリレンダーHTML

## 4. 現在の仕様との関係

### 変更前

- ランディングページの主役デモ、実データ再発、履歴が同じ強さのパネルと表で並び、次に押す場所が目立たない。
- 分析画面で要約、比較グラフ、タイムライン、原因、信号、類似障害、証拠がすべて展開され、主要結論の後も情報密度が高い。
- 情報量は十分だが、一次情報と詳細情報の視覚的な差が小さい。

### 変更後

- ランディングページに主要デモ専用のfeatured cardと明確なCTAを置く。
- 実データ再発と履歴は要約を常時表示し、全行は展開可能な領域に保持する。
- 分析画面では類似度heroと「前回どうしたか」を一次情報として常時表示する。
- Incident Summaryは常時表示し、比較グラフ、タイムライン、原因、信号、全類似候補、証拠を用途別の展開領域へ整理する。
- Analyze/Re-run、全リンク、全データ、グラフ、証拠ジャンプ、モバイル表示を維持する。

## 5. 既存仕様を壊す可能性

- 展開領域に移した情報が発見しにくくなる可能性。
- evidence chipから証拠へ移動するとき、閉じた親detailsが正しく開かない可能性。
- table rowのクリック、Analyze、比較リンク、sparkline tooltipがDOM再編で壊れる可能性。
- プリレンダー版とJavaScript版の情報量が不一致になる可能性。

## 6. 影響するシステム境界

- Web UI
- 画面から既存APIを呼ぶ経路（呼び出し仕様自体は不変）
- ACL、認証、同期、OpenSearch、MCP、Terraform、AWSインフラには影響しない。

## 7. fail-closed を壊す可能性

なし。入力検証、認可、AWSアクセス境界、API処理を変更しない。

## 8. watermark・ledger・orphan cleanup・bulk failure handling への影響

すべて影響なし。フロントエンドの表示構造とCSSのみを変更する。

## 9. 実装しない範囲

- API、データモデル、類似度、AI、fixture、AWSリソースの変更
- 機能、行、フィールド、証拠、グラフ、操作の削除
- 新しいフレームワークや依存関係の追加
- UI文言の事実関係を変える変更

## 10. 後続フェーズに回す範囲

利用者テストによる展開率やタスク完了時間の計測は別フェーズとする。

## 完了条件・検収条件

- ダッシュボード: featured incident、82% match、shared pattern、source、View analysis CTAが最初の画面で理解できる。
- ダッシュボード: real-world 27 cycles、履歴5件、source legendは削除されず閲覧できる。
- 分析画面: Trigger、Analyze/Re-run、82% hero、Why、Differences、What happened last time、Summaryは常時閲覧できる。
- 分析画面: Pattern comparison、Timeline、Suspected Causes、Observed Signals、Similar Incidents、Resolution、Supporting Evidenceは展開して閲覧・操作できる。
- evidence chipを押すとSupporting Evidenceが開き、対象行へ移動する。
- デスクトップとモバイル幅で横方向の破綻がない。
- JavaScriptなしのプリレンダーにも主要デモと全機能説明が残る。

## 設計原則確認

- 既存の静的HTML/CSS/JavaScript構成を維持する。
- 新しい状態管理やライブラリを追加せず、HTMLの`details`を利用する。
- 情報を消さずに優先順位だけを変えるため、一時的回避策ではない。
- TODOや将来削除予定コードを追加しない。

## 代替案比較

### 案A: CSSだけで見た目を整える

- メリット: 変更リスクが最小。
- デメリット: 全情報が同時に表示されるため、根本の情報密度を下げられない。
- 不採用理由: 「伝わりやすいシンプルなUI」という要求を視覚装飾だけでは満たせない。

### 案B: Progressive disclosureで詳細を整理する

- メリット: 主要結論を常時表示し、全機能と全情報を展開領域に保持できる。依存追加不要。
- デメリット: detailsの発見性と、証拠ジャンプ時の展開処理を検証する必要がある。
- 採用理由: 機能削除禁止とシンプル化を同時に満たす最小構造変更。

### 案C: タブや別ページへ分割する

- メリット: 画面ごとの情報量を最も減らせる。
- デメリット: 新しいナビゲーション状態、深いリンク、キーボード操作、履歴管理が増え、主要情報を隠しすぎる。
- 不採用理由: ハッカソンMVPには変更範囲が広く、短時間デモの理解を遅らせる可能性がある。

## 変更影響分析

- 呼び出し元: 公開デモ閲覧者、審査員、AI scoring system。
- 呼び出し先: 既存のincident list/detail/analyze API。APIパスとpayloadは変更しない。
- API互換性: 影響なし。
- テストへの影響: 既存43テストを維持する。テストファイルはユーザー承認なしに変更せず、構造・操作はブラウザで検証する。
- 未確定事項: なし。
